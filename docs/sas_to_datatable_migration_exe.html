SAS → R Migration with data.table

Practical guide: DATA STEP, PROC SQL, PROC FORMAT, and tables

Author

Working notes

1 Introduction

This document brings together the topics discussed: data selection and transformation with data.table, equivalents for SAS DATA STEP and PROC SQL, handling of RETAIN, SAS formats (PROC FORMAT), tabulations, and table production.

All examples are self-contained and reproducible: each code chunk creates the data it needs (or relies on a small set of shared example tables defined in Section 1.0). You can copy any chunk into a fresh R session and run it.

data.table often works by reference: := modifies a table without copying it in full. Use copy() when an independent copy is needed.

2 data.table fundamentals

2.2 General syntax

DT[i, j, by]
  • i: rows to select; conceptually equivalent to WHERE/IF.
  • j: columns to select or expressions to calculate.
  • by: groups, like SAS BY or SQL GROUP BY.

For robust dynamic column selection, ..cols is the idiomatic data.table convention.

2.4 Overview of the symbol [..]

Both of these lines use data.table’s j slot to select or drop columns dynamically — that is, using a character vector instead of writing column names literally. They are the data.table idiom for what would be keep / drop in SAS or select() / select(-...) in dplyr.

# Keep columns by dynamic name
cols <- c("id", "anno", "valore")
DT[, ..cols]

# Drop a column by name
DT[, !c("stato"), with = FALSE]
library(data.table)

DT <- data.table(
  id     = 1:3,
  anno   = 2020:2022,
  valore = c(10, 20, 30),
  stato  = c("A", "B", "A")
)

DT
      id  anno valore  stato
   <int> <int>  <num> <char>
1:     1  2020     10      A
2:     2  2021     20      B
3:     3  2022     30      A

2.5 DT[, ..cols] — select columns by a character vector

cols <- c("id", "anno", "valore")
DT[, ..cols]
      id  anno valore
   <int> <int>  <num>
1:     1  2020     10
2:     2  2021     20
3:     3  2022     30
  • cols is an ordinary R character vector of column names.
  • Inside DT[...], a bare symbol cols would be looked up as a column name in DT (that is data.table’s convention — see the by = and := behavior). Precisely because of that, data.table supports a special prefix: .. means “do not look this up as a column; look it up in the calling environment.”
  • So ..cols expands to list(id, anno, valore) — i.e. it returns a new data.table containing exactly those three columns, in that order.

2.7 When it matters

Any time the column list is computed at runtime — a user-supplied variable list, a loop over column groups, a config file, etc. ..cols is the idiomatic data.table way to say “give me these columns whose names I only know from a variable.”

2.8 Common pitfall

Forgetting the .. gives an error, because data.table first tries to evaluate cols as a column expression:

2.9 DT[, !c("stato"), with = FALSE] — exclude columns by name

DT[, !c("stato"), with = FALSE]
      id  anno valore
   <int> <int>  <num>
1:     1  2020     10
2:     2  2021     20
3:     3  2022     30
  • c("stato") is just the character vector "stato".
  • ! on a character vector means “set difference” in data.table’s j context: !(cols_to_drop) is interpreted as setdiff(names(DT), cols_to_drop).
  • with = FALSE is required here, because without it data.table would try to interpret !c("stato") as a column expression and fail. With with = FALSE, j is evaluated as if it were a character-vector selection — the “drop” semantics.
  • The result is a new data.table with all columns except stato.

2.10 Equivalent / related forms

   <int> <int>  <num>
1:     1  2020     10
2:     2  2021     20
3:     3  2022     30
DT[, setdiff(names(DT), "stato"), with = FALSE]    # explicit

   <int> <int>  <num>
1:     1  2020     10
2:     2  2021     20

Note that := NULL removes the column from DT by reference — that is the data.table counterpart of SAS DROP stato; inside a DATA step, whereas DT[, !"stato", with = FALSE] only returns a new table and leaves DT untouched.

DT_copy <- copy(DT)
DT_copy[, stato := NULL]
names(DT_copy)
[1] "id"     "anno"   "valore"
names(DT)   # original DT is unchanged
[1] "id"     "anno"   "valore" "stato"

2.11 Why with = FALSE matters

In DT[i, j, by], j is normally evaluated as an R expression in the context of DT’s columns:

DT[, id + anno]      # j is an expression, not a name
[1] 2021 2023 2025

But sometimes you want to say “the following character vector is a list of columns.” That is what with = FALSE enables: j is treated as a character vector to select, and the ! prefix means “drop these.” Without with = FALSE, data.table would try to compute !c("stato") as a column-level operation and error out.

2.12 The Power of := (Assignment by Reference) in data.table

In standard R, modifying a dataset usually means creating a hidden copy of it behind the scenes (the “copy-on-modify” behavior). If your dataset is huge, this wastes memory and slows down execution.

The := operator is data.table’s secret weapon. It modifies your data by reference (in-place). Instead of copying millions of rows to change one value, it changes the value directly in your computer’s RAM, making it incredibly fast and memory-efficient.

2.12.1 Key Use Cases with Examples

Below are three examples showcasing how := transforms data manipulation from a high-memory operation into an instantaneous task.

2.12.1.1 Adding or Updating Columns Without Copying

Instead of re-assigning the whole table (df <- df |> mutate(...)), := modifies the table instantly.

library(data.table)

# Create a small dataset
dt <- data.table(
  id = 1:3, 
  sales = c(100, 200, 300)
)

# Add a 'tax' column directly to 'dt' without creating a copy
dt[, tax := sales * 0.22]

print(dt)
      id sales   tax
   <int> <num> <num>
1:     1   100    22
2:     2   200    44
3:     3   300    66

2.12.1.2 Modifying a Subset of Rows Efficiently

In base R, updating a specific subset of rows requires copying the entire matrix. With :=, data.table surgically alters only the rows that match your filter criteria.

# Create a dataset with missing values
employees <- data.table(
  name = c("Alice", "Bob", "Charlie"),
  status = c("Active", "On Leave", "Active"),
  bonus = c(500, NA, 600)
)

# Update bonus ONLY for people 'On Leave' without copying the table
employees[status == "On Leave", bonus := 0]

print(employees)
Index: <status>
      name   status bonus
    <char>   <char> <num>
1:   Alice   Active   500
2:     Bob On Leave     0
3: Charlie   Active   600

2.12.1.3 Updating Multiple Columns Simultaneously

You can update or create multiple columns at once using two different syntaxes depending on your aesthetic preference.

Option A: Using Functional Syntax

dt <- data.table(id = 1:3, mass_kg = c(70, 80, 90))

# Update mass and add a label simultaneously
dt[, `:=`(
  mass_lbs = mass_kg * 2.2,
  checked  = TRUE
)]

Option B: Using Vector Syntax

# The exact same operation using a different layout
dt[, c("mass_lbs", "checked") := .(mass_kg * 2.2, TRUE)]

2.12.2 Why It Matters: Performance Summary

Action Standard R (dplyr/base) data.table with :=
RAM Behavior Copies the whole table into a new memory block. Overwrites/adds fields directly at the same RAM address.
Speed Slows down exponentially as dataset size grows. Remains blistering fast even on 100GB+ tables.
Code Impact Requires assignment back to the variable (x <- ...). No assignment needed; the table changes permanently.

3 SAS / dplyr mental model

Intent SAS dplyr data.table
Keep these columns keep id anno valore; select(id, anno, valore) DT[, .(id, anno, valore)] (literal) or DT[, ..cols] (dynamic)

3.2 Resumé

  • DT[, ..cols] → keep the columns named in the character vector cols. The .. tells data.table “cols lives in the environment, not in the table.”
  • DT[, !c("stato"), with = FALSE] → drop stato and return the rest. ! is “set difference,” and with = FALSE tells data.table that j is a character vector of column names rather than an expression.
  • Neither of the two j-expressions modifies DT; use DT[, col := NULL] if you want in-place removal.

4.6 Update join

An update join (or UPDATE with JOIN) is a database query that modifies or populates columns in one table using related data from a second table based on a matching key or condition. Instead of writing a slow row-by-row loop or a complex subquery, an update join lets you sync or calculate values across tables in a single operation.

4.7 Normal Join vs. Update Join in data.table

The choice between a normal join and an update join in data.table depends entirely on whether you want to create a new dataset or modify an existing one in place.

4.7.1 Normal Join (New Dataset)

A normal join merges two datasets together and returns a completely new object in memory.

  • Behavior: It copies rows and columns from both tables into a third table. The original input dataframes remain untouched.
  • Syntax: ris <- anagrafica[transazioni, on = .(id = id_trans)]
  • Use Case: Best when you need a temporary merged view for a specific analysis, reporting, or when you want to preserve your original source data as-is.

4.7.2 Update Join (In-Place Modification)

An update join uses data from a lookup table to modify or add columns directly inside your main table.

  • Behavior: It updates the data by reference using the := operator. This means it consumes zero extra memory (RAM) because it does not make a copy of the dataset. The primary table is permanently altered.
  • Syntax: transazioni[anagrafica, on = .(id_trans = id), cliente := i.cliente] (Note: the i. prefix explicitly tells R to pull the column from the lookup table inside the bracket).
  • Use Case: Essential when working with large/Big Data datasets where copying millions of rows would cause memory issues, or when your goal is to clean/enrich an existing historical log table.
anagrafica_upd <- copy(anagrafica)
tabella_ref <- data.table(id = c(1L, 3L), classe = c("X", "Y"))

anagrafica_upd[
  tabella_ref,
  on = "id",
  classe := i.classe
]
print(anagrafica_upd)
      id   nome regione classe
   <int> <char>  <char> <char>
1:     1   Anna     Sud      X
2:     2  Bruno    Nord   <NA>
3:     3  Carla  Centro      Y
4:     4  Dario    Nord   <NA>

Watch join cardinality: if the lookup table contains multiple rows per key, the join can multiply rows. Check beforehand:

Check interval endpoints carefully: SAS supports ranges and inclusion options that may not match cut() defaults. Handle missing values explicitly as well.

7.3 Complex formats: lookup table

For long formats or catalog-driven formats, a lookup table is often preferable:

DT[formato, sesso_label := i.label, on = .(sesso = codice)]
DT[is.na(sesso_label), sesso_label := "Non classificato"]

7.4 SAS and R missing values

SAS distinguishes the ordinary numeric missing . from special missings .A–.Z (and ._). In R, the standard value is NA and NaN has a distinct semantics, but it does not directly represent the whole set of SAS special missings.

If such distinctions have statistical or administrative meaning, preserve them during import with an explicit coding (for example a status variable or a textual representation) before normalizing values.

7.5 PUT() and INPUT()

  • SAS PUT() applies a format and returns a representation, often character.
  • SAS INPUT() reads a string using an informat and converts the value.

In R, the equivalent depends on the format: lookup tables or fcase() for discrete codes; as.integer(), as.numeric(), or parsing functions for conversions; format() for text representations — do not assume it reproduces every SAS format.

8 Labels and data dictionary

For migration projects, distinguish: 1. variable name; 2. descriptive label; 3. value coding; 4. source type and format; 5. missing-value rules.

A metadata table might contain these columns:

10 Checklist for a SAS → data.table migration

  1. Data order: check every BY, FIRST./LAST., LAG(), and RETAIN.
  2. Missing values: compare SAS . and special missing values with R NA/NaN.
  3. Joins: check key cardinality and duplicates.
  4. Types: check character/numeric/date conversions and overflow.
  5. Formats: distinguish data coding from display labels.
  6. Aggregations: verify denominators and missing-value behavior.
  7. Output: compare SAS and R results on validation samples and edge cases.
  8. Performance: use :=, setorder(), keyed joins, and grouped aggregations; avoid unnecessary copies.
