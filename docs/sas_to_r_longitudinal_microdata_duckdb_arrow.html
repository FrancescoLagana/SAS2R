SAS to R: Longitudinal Microdata Processing with DuckDB and Arrow

A practical guide to scalable longitudinal transformations using DuckDB and Apache Arrow

Author

Francesco Laganà

Published

November 11, 2026

1 Purpose and scope

This guide translates common SAS DATA-step patterns for longitudinal microdata into R workflows based on DuckDB and Apache Arrow. The examples focus on operations performed within individuals over time:

  • ordering records and identifying the first and last observation;
  • retaining previous values and comparing adjacent waves;
  • calculating cumulative values and event counters;
  • detecting status changes and constructing spells;
  • identifying first and last non-missing values;
  • calculating transitions and individual-level indicators;
  • carrying values forward;
  • constructing balanced panels;
  • validating one-row-per-person-period data.

The two technologies have related but different roles:

  • DuckDB is an analytical database engine. It executes SQL, including window functions, directly against Parquet files without requiring the full dataset to be loaded into R memory.
  • Arrow provides an in-memory columnar format and a dataset interface. It can scan partitioned Parquet data, project and filter columns, and execute supported transformations lazily. Some longitudinal window operations are not available for every Arrow Dataset query. In those cases, collect the relevant data into an Arrow Table/R object or use DuckDB.

The examples use id for the individual identifier, year for the observation period, and status, income, and weight as illustrative variables. Replace them with the variables in the production data.

1.3 Open the data with DuckDB and Arrow

  • DuckDB
  • Arrow
con <- dbConnect(duckdb::duckdb(), dbdir = ":memory:")

# A view over the Parquet file; the records are not copied into an R data.frame.
dbExecute(con, "
  CREATE OR REPLACE VIEW have AS
  SELECT *
  FROM read_parquet('Data/longitudinal_example.parquet')
")

dbGetQuery(con, "SELECT * FROM have ORDER BY id, year")
ds <- open_dataset("Data/longitudinal_example.parquet", format = "parquet")

ds |>

Important: DuckDB and Arrow do not automatically impose a row order. Whenever an operation depends on chronology, specify ORDER BY id, year in SQL or arrange(id, year) in a supported Arrow/R workflow.

2 SAS BY, FIRST. and LAST.

2.1 What SAS creates

proc sort data=have;
  by id year;
run;

data want;
  set have;
  by id;
  if first.id then first_record = 1;
  else first_record = 0;

  if last.id then last_record = 1;
  else last_record = 0;
run;

FIRST.id is 1 on the first observation in each individual group; LAST.id is 1 on the last. In a multi-variable BY statement, SAS also creates indicators for the boundaries of each BY-group level.

2.2 Flag the first and last record of each individual

  • DuckDB
  • Arrow
dbGetQuery(con, "
  SELECT
    id, year, status, income,
    ROW_NUMBER() OVER (
      PARTITION BY id ORDER BY year
    ) = 1 AS first_record,
    ROW_NUMBER() OVER (
      PARTITION BY id ORDER BY year DESC
    ) = 1 AS last_record
  FROM have
  ORDER BY id, year
")

The ROW_NUMBER() window function numbers records within each individual. The first and last positions can then be flagged.

# Window functions on a Dataset are not supported consistently across
# Arrow versions/backends. Collect the projected columns, then use dplyr.
arrow_data <- ds |>
  select(id, year, status, income) |>
  collect()

arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  mutate(
    first_record = row_number() == 1L,
    last_record  = row_number() == n()
  ) |>
  ungroup()

2.3 Keep only the first or last record

  • DuckDB
  • Arrow
firsts <- dbGetQuery(con, "
  SELECT * EXCLUDE (rn)
  FROM (
    SELECT *, ROW_NUMBER() OVER (
      PARTITION BY id ORDER BY year
    ) AS rn
    FROM have
  )
  WHERE rn = 1
  ORDER BY id
")

lasts <- dbGetQuery(con, "
  SELECT * EXCLUDE (rn)
  FROM (
    SELECT *, ROW_NUMBER() OVER (
      PARTITION BY id ORDER BY year DESC
    ) AS rn
    FROM have
  )
  WHERE rn = 1
  ORDER BY id
")

firsts
lasts
arrow_data <- ds |>
  select(id, year, status, income, weight) |>
  collect() |>
  arrange(id, year)

firsts <- arrow_data |>

4 RETAIN: carry a value across observations

4.1 The SAS pattern

RETAIN prevents a DATA-step variable from being reset to missing at the beginning of each iteration. It is often used for previous values, running totals, state flags, and spell identifiers.

data want;
  set have;
  by id year;
  retain previous_income;

  if first.id then previous_income = .;
  output;
  previous_income = income;
run;

The output occurs before previous_income is updated. Therefore, the current output row contains the income from the previous observation of the same individual.

4.2 Previous and next observation: LAG() and LEAD()

  • DuckDB
  • Arrow
dbGetQuery(con, "
  SELECT
    id, year, income,
    LAG(income) OVER (
      PARTITION BY id ORDER BY year
    ) AS previous_income,
    LEAD(income) OVER (
      PARTITION BY id ORDER BY year
    ) AS next_income
  FROM have
  ORDER BY id, year
")

PARTITION BY id restarts the window for each individual. The first previous value and last next value are NULL (which becomes NA when returned to R).

# Collect before applying grouped window functions. This is the portable
# approach for Arrow Dataset workflows.
arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  mutate(
    previous_income = lag(income),
    next_income     = lead(income)
  ) |>
  ungroup()

SAS pitfall: SAS LAG() is a queue function. It advances only when the function is executed. SQL LAG() and R lag() are window/positional operations, so conditional calls in SAS should not be translated mechanically.

5 Running totals and cumulative calculations

5.1 Running total within each individual

  • DuckDB
  • Arrow
dbGetQuery(con, "
  SELECT *,
         SUM(COALESCE(income, 0)) OVER (
           PARTITION BY id
           ORDER BY year
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
         ) AS cumulative_income
  FROM have
  ORDER BY id, year
")

COALESCE(income, 0) treats missing income as zero for this calculation. Remove it if missing values should be ignored without being explicitly recoded.

arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  mutate(cumulative_income = cumsum(coalesce(income, 0))) |>
  ungroup()

5.2 Running count of non-missing values

  • DuckDB
  • Arrow
dbGetQuery(con, "
  SELECT *,
         COUNT(income) OVER (
           PARTITION BY id
           ORDER BY year
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
         ) AS n_income_observed
  FROM have
  ORDER BY id, year
")
arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  mutate(n_income_observed = cumsum(!is.na(income))) |>
  ungroup()

5.3 Running maximum or minimum

  • DuckDB
  • Arrow
dbGetQuery(con, "
  SELECT *,
         MAX(income) OVER (
           PARTITION BY id ORDER BY year
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
         ) AS running_max_income,
         MIN(income) OVER (
           PARTITION BY id ORDER BY year
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
         ) AS running_min_income
  FROM have
  ORDER BY id, year
")
arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  mutate(
    running_max_income = cummax(income),
    running_min_income = cummin(income)
  ) |>
  ungroup()

6 Comparing the current record with the previous record

6.1 Difference from previous wave

  • DuckDB
  • Arrow
dbGetQuery(con, "
  SELECT *,
         income - LAG(income) OVER (
           PARTITION BY id ORDER BY year
         ) AS change_income
  FROM have
  ORDER BY id, year
")
arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  mutate(
    previous_income = lag(income),
    change_income = income - previous_income
  ) |>
  ungroup()

6.2 Flag a change in categorical status

  • DuckDB
  • Arrow
dbGetQuery(con, "
  WITH x AS (
    SELECT *,
           LAG(status) OVER (
             PARTITION BY id ORDER BY year
           ) AS previous_status
    FROM have
  )
  SELECT *,
         CASE
           WHEN previous_status IS NULL THEN FALSE
           WHEN status IS DISTINCT FROM previous_status THEN TRUE
           ELSE FALSE
         END AS status_changed
  FROM x
  ORDER BY id, year
")

IS DISTINCT FROM compares values while treating NULL explicitly. It is safer than <> when missing values are possible.

arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  mutate(
    previous_status = lag(status),
    status_changed = !is.na(previous_status) &
      (status != previous_status)
  ) |>
  ungroup()

7 Detecting first occurrence, last occurrence, and extrema

7.1 First observed non-missing value per individual

  • DuckDB
  • Arrow
dbGetQuery(con, "
  SELECT *,
         FIRST_VALUE(income IGNORE NULLS) OVER (
           PARTITION BY id
           ORDER BY year
         ) AS first_observed_income
  FROM have
  ORDER BY id, year
")

IGNORE NULLS skips missing values when finding the first observed income. Check the DuckDB version used in production when relying on optional SQL syntax.

arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  mutate(
    first_observed_income = {
      z <- income[!is.na(income)]
      if (length(z) == 0L) NA_real_ else z[1L]
    }
  ) |>
  ungroup()

7.2 First year in which a condition is satisfied

For example, identify the first year in which income is at least 3,000.

  • DuckDB
  • Arrow
dbGetQuery(con, "
  SELECT id,
         MIN(year) FILTER (WHERE income >= 3000) AS first_year_income_3000
  FROM have
  GROUP BY id
  ORDER BY id
")
arrow_data |>
  group_by(id) |>
  summarise(
    first_year_income_3000 = {
      y <- year[!is.na(income) & income >= 3000]
      if (length(y) == 0L) NA_integer_ else min(y)
    },
    .groups = "drop"
  )

7.3 Last non-missing value

  • DuckDB
  • Arrow
dbGetQuery(con, "
  SELECT *,
         LAST_VALUE(income IGNORE NULLS) OVER (
           PARTITION BY id
           ORDER BY year
           ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
         ) AS last_observed_income
  FROM have
  ORDER BY id, year
")
arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  mutate(
    last_observed_income = {
      z <- income[!is.na(income)]
      if (length(z) == 0L) NA_real_ else z[length(z)]
    }
  ) |>
  ungroup()

8 Constructing spells and episodes

A spell is a consecutive sequence of observations in which a state remains unchanged. The definition of consecutive must be explicit: it can mean consecutive rows or consecutive calendar years.

8.1 Start a new spell whenever status changes

  • DuckDB
  • Arrow
dbGetQuery(con, "
  WITH previous AS (
    SELECT *,
           LAG(status) OVER (
             PARTITION BY id ORDER BY year
           ) AS previous_status
    FROM have
  ),
  marked AS (
    SELECT *,
           CASE
             WHEN previous_status IS NULL THEN 1
             WHEN status IS DISTINCT FROM previous_status THEN 1
             ELSE 0
           END AS new_spell
    FROM previous
  )
  SELECT *,
         SUM(new_spell) OVER (
           PARTITION BY id ORDER BY year
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
         ) AS spell_id
  FROM marked
  ORDER BY id, year
")
arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  mutate(
    previous_status = lag(status),
    new_spell = is.na(previous_status) |
      is.na(status) |
      status != previous_status,
    spell_id = cumsum(new_spell)
  ) |>
  ungroup()

If missing status values have a specific substantive meaning, define the transition rule explicitly. The Arrow example treats a missing status as a boundary; it does not silently equate missing with a valid category.

8.2 Start a new spell after a gap in observation years

  • DuckDB
  • Arrow
dbGetQuery(con, "
  WITH previous AS (
    SELECT *,
           LAG(year) OVER (
             PARTITION BY id ORDER BY year
           ) AS previous_year
    FROM have
  ),
  marked AS (
    SELECT *,
           CASE
             WHEN previous_year IS NULL THEN 1
             WHEN year - previous_year > 1 THEN 1
             ELSE 0
           END AS new_spell
    FROM previous
  )
  SELECT *,
         SUM(new_spell) OVER (
           PARTITION BY id ORDER BY year
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
         ) AS spell_id
  FROM marked
  ORDER BY id, year
")
arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  mutate(
    previous_year = lag(year),
    new_spell = is.na(previous_year) | (year - previous_year > 1L),
    spell_id = cumsum(new_spell)
  ) |>
  ungroup()

8.3 Summarise each spell

Assume spell_id has been created by one of the preceding examples.

  • DuckDB
  • Arrow
dbGetQuery(con, "
  SELECT id, status,
         MIN(year) AS spell_start,
         MAX(year) AS spell_end,
         COUNT(*) AS n_records
  FROM (
    SELECT *,
           SUM(new_spell) OVER (
             PARTITION BY id ORDER BY year
           ) AS spell_id
    FROM (
      SELECT *,
             CASE
               WHEN LAG(status) OVER (
                 PARTITION BY id ORDER BY year
               ) IS DISTINCT FROM status THEN 1
               WHEN ROW_NUMBER() OVER (
                 PARTITION BY id ORDER BY year
               ) = 1 THEN 1
               ELSE 0
             END AS new_spell
      FROM have
    )
  )
  GROUP BY id, spell_id, status
  ORDER BY id, spell_id
")
spells_arrow <- arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  mutate(
    previous_status = lag(status),
    new_spell = row_number() == 1L |
      is.na(status) | is.na(previous_status) |
      status != previous_status,
    spell_id = cumsum(new_spell)
  ) |>
  ungroup()

spells_arrow |>
  group_by(id, spell_id, status) |>
  summarise(
    spell_start = min(year),
    spell_end = max(year),
    n_records = n(),
    .groups = "drop"
  )

9 Transition matrices and state histories

9.1 Previous-to-current status transition

  • DuckDB
  • Arrow
dbGetQuery(con, "
  WITH transitions AS (
    SELECT
      id, year, status,
      LAG(status) OVER (
        PARTITION BY id ORDER BY year
      ) AS previous_status
    FROM have
  )
  SELECT previous_status, status, COUNT(*) AS n
  FROM transitions
  WHERE previous_status IS NOT NULL
  GROUP BY previous_status, status
  ORDER BY previous_status, status
")
arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  mutate(previous_status = lag(status)) |>
  ungroup() |>
  filter(!is.na(previous_status)) |>
  count(previous_status, status, name = "n") |>
  arrange(previous_status, status)

9.2 Individual-level transition indicator

For example, flag individuals who ever move from status A to status B.

  • DuckDB
  • Arrow
dbGetQuery(con, "
  WITH transitions AS (
    SELECT
      id,
      LAG(status) OVER (
        PARTITION BY id ORDER BY year
      ) AS previous_status,
      status
    FROM have
  )
  SELECT id,
         BOOL_OR(previous_status = 'A' AND status = 'B') AS ever_A_to_B
  FROM transitions
  GROUP BY id
  ORDER BY id
")
arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  mutate(previous_status = lag(status)) |>
  summarise(
    ever_A_to_B = any(
      previous_status == "A" & status == "B",
      na.rm = TRUE
    ),
    .groups = "drop"
  )

10 Within-individual transformations and baseline values

10.1 Deviation from the first observed value

  • DuckDB
  • Arrow
dbGetQuery(con, "
  SELECT *,
         income - FIRST_VALUE(income) OVER (
           PARTITION BY id ORDER BY year
         ) AS deviation_from_first
  FROM have
  ORDER BY id, year
")

If the first record can have missing income, use a first-non-missing-value expression rather than FIRST_VALUE(income).

arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  mutate(
    baseline_income = first(income),
    deviation_from_first = income - baseline_income
  ) |>
  ungroup()

10.2 Within-individual mean and centring

  • DuckDB
  • Arrow
dbGetQuery(con, "
  SELECT *,
         AVG(income) OVER (PARTITION BY id) AS mean_income_id,
         income - AVG(income) OVER (PARTITION BY id) AS centred_income
  FROM have
  ORDER BY id, year
")
arrow_data |>
  group_by(id) |>
  mutate(
    mean_income_id = mean(income, na.rm = TRUE),
    centred_income = income - mean_income_id
  ) |>
  ungroup()

10.3 Within-individual rank

  • DuckDB
  • Arrow
dbGetQuery(con, "
  SELECT *,
         RANK() OVER (
           PARTITION BY id ORDER BY income
         ) AS income_rank
  FROM have
  ORDER BY id, year
")
arrow_data |>
  group_by(id) |>
  mutate(income_rank = min_rank(income)) |>
  ungroup()

11 Conditional carry-forward and last observation carried forward

A common longitudinal task is to propagate the most recent non-missing value within an individual. This is often called LOCF (last observation carried forward). The operation must not carry values across individuals.

  • DuckDB
  • Arrow
dbGetQuery(con, "
  SELECT *,
         LAST_VALUE(income IGNORE NULLS) OVER (
           PARTITION BY id
           ORDER BY year
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
         ) AS income_locf
  FROM have
  ORDER BY id, year
")
arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  tidyr::fill(income, .direction = "down") |>
  rename(income_locf = income) |>
  ungroup()

The Arrow example uses tidyr::fill() after collecting the data into an R object. For very large datasets, consider performing LOCF in DuckDB to avoid materialising the full dataset in R.

12 Conditional accumulation and event counters

12.1 Count events to date

Suppose an event is defined as a transition into status B.

  • DuckDB
  • Arrow
dbGetQuery(con, "
  WITH x AS (
    SELECT *,
           LAG(status) OVER (
             PARTITION BY id ORDER BY year
           ) AS previous_status,
           ROW_NUMBER() OVER (
             PARTITION BY id ORDER BY year
           ) AS row_num
    FROM have
  ),
  y AS (
    SELECT *,
      CASE
        WHEN previous_status IS NULL THEN NULL
        WHEN status IS NULL THEN NULL
        WHEN status = 'B'
         AND previous_status IS DISTINCT FROM 'B' THEN 1
        ELSE 0
      END AS entry_into_B
    FROM x
  )
  SELECT *,
    SUM(COALESCE(entry_into_B, 0)) OVER (
      PARTITION BY id ORDER BY year
      ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS observed_entries_into_B
  FROM y
  ORDER BY id, year
")
arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  mutate(
    previous_status = lag(status),
    event = status == "B" &
      (is.na(previous_status) | previous_status != "B"),
    event = coalesce(event, FALSE),
    entries_into_B = cumsum(event)
  ) |>
  ungroup()

12.2 Count records satisfying a condition

  • DuckDB
  • Arrow
dbGetQuery(con, "
  SELECT *,
         SUM(CASE WHEN income >= 3000 THEN 1 ELSE 0 END) OVER (
           PARTITION BY id ORDER BY year
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
         ) AS n_years_income_3000
  FROM have
  ORDER BY id, year
")
arrow_data |>
  arrange(id, year) |>
  group_by(id) |>
  mutate(
    n_years_income_3000 = cumsum(
      !is.na(income) & income >= 3000
    )
  ) |>
  ungroup()

13 Multi-row state logic: when a loop is appropriate

Not every longitudinal transformation is naturally expressed as a single window function. A sequential loop may be appropriate when the next state depends on several conditions evaluated using the state built by previous rows.

Before writing a loop, check whether the operation can be expressed as:

  1. a LAG()/LEAD() window function;
  2. a cumulative sum or cumulative maximum;
  3. a conditional window aggregate;
  4. a spell identifier followed by a grouped summary.

DuckDB is generally preferable for stateful operations on large Parquet datasets when the logic can be translated into SQL window functions. Arrow is useful for scanning and filtering the source data, but complex sequential state logic may require collection or a different execution engine.

15 Construct a balanced panel

A balanced panel contains one row for every individual-period combination in the chosen observation window. The example below creates all years between 2019 and 2023 for every individual observed in the source.

  • DuckDB
  • Arrow
dbGetQuery(con, "
  WITH ids AS (
    SELECT DISTINCT id FROM have
  ),
  years AS (
    SELECT * FROM range(2019, 2024) AS t(year)
  )
  SELECT ids.id, years.year
  FROM ids
  CROSS JOIN years
  ORDER BY ids.id, years.year
")

To add observed variables, left join the balanced grid to the original data:

dbGetQuery(con, "
  WITH ids AS (
    SELECT DISTINCT id FROM have
  ),
  years AS (
    SELECT * FROM range(2019, 2024) AS t(year)
  ),
  panel AS (
    SELECT ids.id, years.year
    FROM ids CROSS JOIN years
  )
  SELECT panel.id, panel.year, have.status, have.income
  FROM panel
  LEFT JOIN have USING (id, year)
  ORDER BY panel.id, panel.year
")
# Collect distinct identifiers and years to construct the grid in R.
ids <- ds |>
  distinct(id) |>
  collect()

years <- tibble::tibble(year = 2019:2023)

For large longitudinal files, avoid reading all columns and all rows if the operation needs only a subset. Projection (selecting columns) and predicate pushdown (filtering rows) reduce I/O.

  • Arrow
dbGetQuery(con, "

  select(id, year, income) |>

17 Validation: one row per individual-period

A production longitudinal file should be checked for duplicate keys, missing identifiers, unexpected periods, and implausible sequences.

  • DuckDB
  • Arrow
# Duplicate id-year combinations
dbGetQuery(con, "
  SELECT id, year, COUNT(*) AS n
  FROM have
  GROUP BY id, year
  HAVING COUNT(*) > 1
  ORDER BY id, year
")
# Missing identifiers or periods
dbGetQuery(con, "
  SELECT
    COUNT(*) FILTER (WHERE id IS NULL) AS missing_id,
    COUNT(*) FILTER (WHERE year IS NULL) AS missing_year,
    COUNT(*) AS n_records
  FROM have
")
arrow_data |>
  count(id, year) |>
  filter(n > 1)
arrow_data |>
  summarise(
    missing_id = sum(is.na(id)),
    missing_year = sum(is.na(year)),
    n_records = n()
  )

18 Important migration pitfalls

18.1 SQL NULL and R NA

DuckDB uses SQL NULL; values returned to R are generally represented as NA. SQL comparisons involving NULL can return an unknown result. Use IS NULL, IS NOT NULL, COALESCE(), or IS DISTINCT FROM as appropriate.

18.2 Missing values in cumulative calculations

Decide whether a missing value should: - contribute zero; - be ignored; - make the cumulative result missing from that point onward; - or be treated as a distinct state.

These choices are not interchangeable. In SQL, SUM() ignores NULL, while COALESCE(x, 0) explicitly converts it to zero. In R, cumsum() propagates NA unless the vector is recoded first.

18.3 Ordering and ties

Window functions require an explicit ORDER BY. If multiple records share the same id and year, the ordering is not deterministic unless another tie-breaker is supplied. This matters for LAG(), LEAD(), ROW_NUMBER(), and spell construction.

18.4 Arrow Dataset versus Arrow Table

open_dataset() creates a lazy dataset interface. Many projections, filters, and aggregations can be pushed down to the Parquet scan. However, not every R/dplyr operation is supported by every Arrow Dataset backend/version. collect() materialises the result in R memory. Use it deliberately, preferably after filtering and selecting the required columns.

18.5 DuckDB connection lifecycle

A DuckDB connection is opened once and reused for multiple queries. Close it when the work is finished:

dbDisconnect(con, shutdown = TRUE)

For an in-memory database, disconnecting with shutdown = TRUE shuts down the DuckDB instance. For a persistent database, set dbdir to a file path instead of ":memory:".

19 Recommended production pattern

For large annual register transformations, a practical architecture is:

  1. Inspect and filter with DuckDB or Arrow: read only the required Parquet columns and periods.
  2. Use DuckDB for longitudinal windows: LAG, LEAD, ROW_NUMBER, cumulative aggregates, spell IDs, and transitions.
  3. Use Arrow for columnar interchange and Parquet datasets: scanning, projection, filtering, partitioned output, and exchange with other tools.
  4. Materialise only when needed: collect small validation tables or selected subsets into R.
  5. Validate every transformation: key uniqueness, row counts, missingness, period coverage, and consistency of derived states.

For a transformation pipeline that is dominated by sequential longitudinal operations, DuckDB can often perform the entire transformation directly on Parquet. Arrow remains valuable for efficient dataset access and data interchange; it does not need to duplicate every DuckDB operation.
