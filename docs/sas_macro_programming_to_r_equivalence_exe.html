SAS Macro Programming and R: An Equivalence Guide

Concepts, patterns, and migration strategies

# Purpose and scope

SAS macro programming and R solve overlapping but not identical problems.

  • SAS macro language is a text-generation and code-parameterization system. Macro statements execute before the generated SAS code is compiled and run.
  • R is a general-purpose programming language. Its functions, arguments, environments, control flow, and data structures usually provide a more direct and maintainable way to express the same logic.
  • The R package macro provides a SAS-inspired macro preprocessor for R. It may help with compatibility-oriented translations, but it is not the default recommendation for new R code.

This guide focuses on practical equivalence: how to translate macro-driven SAS workflows into idiomatic R, while also identifying where a literal macro-style translation may be useful.

2 The mental model

2.1 SAS macro processing

A typical SAS macro workflow has two layers:

  1. Macro processor resolves macro variables and executes macro statements.
  2. The resulting SAS text is submitted to the SAS compiler/runtime.
%let year = 2025;

%macro summarize(data=, year=);

  proc means data=&data;
    where year = &year;
  run;
  
%mend;

%summarize(data=work.population, year=&year)

The macro generates SAS source text. &year is substituted before the procedure runs.

2.2 Idiomatic R

In R, the usual equivalent is a function with explicit arguments:

summarize_data <- function(data, year) {
subset_data <- data[data$year == year, , drop = FALSE]
summary(subset_data)
}

summarize_data(people, year = 2025)

3 Core equivalence table

SAS macro feature Typical purpose Idiomatic R equivalent Notes
%LET name=value; Define macro variable name <- value R objects have types; macro variables are text
&name Resolve macro variable Use object/argument name No textual substitution needed in ordinary R
%MACRO ... %MEND; Define reusable generator function(...) {} Function returns values or performs explicit work
%macro(arg=val) Invoke macro fun(arg = val) Named arguments are usually clearer
%IF ... %THEN Conditional code generation if (...) {} R condition must be a length-one logical
%ELSE Alternative branch else {} Standard R control flow
%DO i=1 %TO n; Repeated generation for (i in seq_len(n)) {} seq_len(0) safely returns integer(0)
%DO %WHILE(...) Conditional repetition while (...) {} Use explicit state updates
%DO %UNTIL(...) Repeat until condition repeat { ...; if (cond) break } R has no direct until statement
%SYSFUNC(f(...)) Call DATA step function in macro processor Call R function f(...) R functions operate on typed values
%SYSEVALF(expr) Evaluate numeric expression eval() or ordinary arithmetic Prefer direct arithmetic; eval() is rarely needed
%EVAL(expr) Integer expression evaluation Integer arithmetic / as.integer() Be explicit about numeric types
%STR(...), %NRSTR(...) Mask macro special characters Character strings / quoting R string literals use quotes and escapes
%SUPERQ(name) Protect macro-variable value Pass character value as data Avoid code construction where possible
%UNQUOTE(...) Remove macro quoting Usually unnecessary R does not have SAS macro quoting semantics
%LOCAL Local macro variable scope Function-local variables R lexical scoping differs; assignments can create local bindings
%GLOBAL Global macro variable Global environment assignment Avoid <<- unless intentional
%PUT Write to SAS log message(), cat(), print() message() is often suitable for diagnostics
%INCLUDE file; Include SAS source source("file.R") source() evaluates code in an environment
CALL SYMPUTX Create/update macro variable from DATA step Return value; assign to object Avoid hidden cross-step state
SYMGET Read macro variable in DATA step Read an object/argument In R, pass dependencies explicitly
SYMEXIST Test macro variable existence exists("name", envir = env) Use explicit environment if needed
PROC SQL INTO :var Store query result in macro variable Assign query result to R object Result may be vector, data frame, or scalar
&var. Delimited macro reference R object reference SAS period delimiter has no direct R equivalent
&&name&i Indirect/nested resolution List/vector indexing or named lookup Replace generated names with structured objects
Macro-generated PROC/DATA steps Generate many SAS steps Function + loop / map Consider one vectorized operation first

# Macro variables: %LET and &name

## SAS

%let input_ds = work.people;
%let reference_year = 2025;

proc freq data=&input_ds;
  tables sex;
  where year = &reference_year;
run;

3.1 R

input_data     <- people
reference_year <- 2025

table(input_data$sex[input_data$year == reference_year])

F M 
2 1

3.1.1 Important difference

SAS macro variables are fundamentally character text. R objects can be numeric, logical, character, lists, or data frames. Prefer keeping values typed in R rather than converting everything to strings.

If a character value is intended as a literal, keep it as a character value:

region <- "Bern"
region
[1] "Bern"

4 Macro definitions and parameters

4.1 SAS

%macro tabulate(data=, variable=);
  proc freq data=&data;
    tables &variable;
  run;
%mend;

%tabulate(data=work.people, variable=sex)

4.2 R function

tabulate_variable <- function(data, variable) {
  table(data[[variable]], useNA = "ifany")
}

tabulate_variable(people, "sex")

F M 
5 5

For reusable R code, prefer a function argument that identifies a column by name, or use a well-documented tidy-evaluation interface. The data[[variable]] pattern is explicit and works well when variable is a character string.

5 5. Conditional logic: %IF / %ELSE

5.1 SAS

%macro choose(data=, mode=);

  %if %upcase(&mode) = FULL %then %do;
    proc means data=&data;
    run;
  %end;
  %else %do;
    proc freq data=&data;
    run;
  %end;
  
%mend;

5.2 R

choose_summary <- function(data, mode = "FULL") {
  mode <- toupper(mode)
  
  if (mode == "FULL") {
    summary(data)
  } else {
    lapply(data, function(x) if (is.factor(x)) table(x) else NULL)
  }
}

6 Iteration: %DO

6.1 Numeric loop

SAS:

%macro run_years(first=, last=);

  %do year = &first %to &last;
    %put Processing &year;
  %end;
  
%mend;

%run_years(first=2020, last=2025)

R:

run_years <- function(first, last) {
for (year in seq.int(first, last)) {
  message("Processing ", year)
}
}

run_years(2020, 2025)
Processing 2020
Processing 2021
Processing 2022
Processing 2023
Processing 2024
Processing 2025

For loops that may have zero iterations, use seq_len(n):

n <- 0L
for (i in seq_len(n)) {
# work
}
message("Number of iterations with n = 0: ", length(seq_len(n)))
Number of iterations with n = 0: 0

Avoid 1:n when n may be zero: in R, 1:0 is c(1, 0), not an empty sequence.

6.2 Iterating over a list of values

SAS often creates one step per value:

%let vars = age income education;

R:

vars <- c("age", "income", "education")

for (variable in vars) {
  message("Processing variable: ", variable)
}
Processing variable: age
Processing variable: income
Processing variable: education

If the task can be vectorized or grouped in one operation, that may be simpler and faster than generating repeated code.

7 %SYSFUNC, %EVAL, and %SYSEVALF

SAS:

%let next_year = %sysfunc(sum(&year, 1));
%let is_valid = %eval(&year >= 2020);

R:

year      <- 2025
next_year <- year + 1
is_valid  <- year >= 2020

next_year
[1] 2026
is_valid
[1] TRUE

R normally evaluates arithmetic and logical expressions directly. eval() is not the routine equivalent of %EVAL; it evaluates an R language object in an environment and should only be used when dynamic evaluation is genuinely required.

8 Local and global scope: %LOCAL / %GLOBAL

SAS:

%macro example();

  %local temp;
  %let temp = 10;
  %put &=temp;
  
%mend;

R:

example_scope <- function() {
temp <- 10
message("temp = ", temp)
}

example_scope()
temp = 10

R function assignments are local by default. SAS %GLOBAL is sometimes approximated by assignment in .GlobalEnv, but global mutation is usually less maintainable than returning a value.

result <- function() {
  value <- 10
  value
}

x <- result()
x
[1] 10

<<- searches parent environments and updates an existing binding; it is not a general-purpose replacement for %GLOBAL.

9 Indirect references: &&name&i

SAS macro code may use indirect resolution:

%let name1 = age;
%let name2 = income;

%MACRO print_names;

%do i = 1 %to 2;
  %put &&name&i;
%end;

%MEND;

In R, use a vector or list rather than constructing variable names:

variable_names <- c("age", "income")

for (variable in variable_names) {
  print(variable)
}
[1] "age"
[1] "income"

For multiple objects, prefer a named list:

datasets <- list(
baseline = baseline_data,
followup = followup_data
)

datasets[["baseline"]]
  id score
1  1    10
2  2    20
3  3    30
4  4    40
5  5    50

Avoid patterns such as get(paste0("data", i)) when a list would express the structure directly.

10 CALL SYMPUTX, SYMGET, and PROC SQL INTO

10.1 SAS

data _null_;
  set work.people end=last;
  if last then call symputx("n_obs", _n_);
run;

%put Number of observations: &n_obs;

10.2 R

n_obs <- nrow(people)
message("Number of observations: ", n_obs)
Number of observations: 10

SAS SQL:

proc sql noprint;
  select count(*) into :n_obs
  from work.people;
quit;

R:

n_obs <- nrow(people)
n_obs
[1] 10

The R equivalent is usually a direct assignment. If a database is involved, use the database query result as an R object rather than routing it through a macro variable.

11 %INCLUDE and modular code

For larger R projects, consider package structure, explicit function exports, and project-relative paths (for example, with the here package) instead of relying on the current working directory.

12 Text generation versus data-driven programming

A macro may generate a different variable name or procedure for each iteration. In R, first consider whether the operation can be expressed as:

  • a function applied to a vector of names;
  • a list of inputs and outputs;
  • a grouped or vectorized data transformation;
  • a single model call with formula construction;
  • a loop that calls a function, rather than creating source code.

Example: process several variables.

SAS:

%macro describe(data=, vars=);

  %do i = 1 %to %sysfunc(countw(&vars));
  
    %let var = %scan(&vars, &i);
    
    proc means data=&data;
      var &var;
    run;
    
  %end;
  
%mend;

R:

describe_vars <- function(data, vars) {
lapply(vars, function(variable) {
  x <- data[[variable]]
  if (!is.numeric(x)) {
    return(c(n = sum(!is.na(x)), mean = NA_real_, sd = NA_real_))
  }
  c(
    n    = sum(!is.na(x)),
    mean = mean(x, na.rm = TRUE),
    sd   = sd(x, na.rm = TRUE)
  )
}) |>
  stats::setNames(vars)
}

describe_vars(people, c("age", "income"))
$age
       n     mean       sd 
10.00000 43.50000 23.13367 

$income

   8.000 1962.500 1349.008

This returns structured results rather than producing repeated source text.

13 SAS macro quoting and R strings

SAS macro quoting functions (%STR, %NRSTR, %BQUOTE, %NRBQUOTE, %SUPERQ, %UNQUOTE) protect characters from macro interpretation. They do not have one-to-one equivalents in R.

In R, strings are data:

text_value <- "A value containing &, %, commas, and spaces"
text_value
[1] "A value containing &, %, commas, and spaces"

When generating code, distinguish carefully between: - a character value; - an R symbol; - an R language expression; - source text.

Prefer constructing language objects with call(), as.name(), or formula interfaces only when necessary. Avoid concatenating untrusted values into executable source code.

14 When the R macro package may be relevant

The R package macro offers a SAS-inspired macro preprocessor. It can be useful when: - a team needs to preserve macro-like syntax during a staged migration; - a large codebase contains extensive macro-driven source generation; - a compatibility layer is deliberately part of the migration plan.

It should not be assumed to provide complete SAS macro processor compatibility. Validate syntax and behavior against the package’s current documentation and test representative edge cases. For new R development, native functions and ordinary R control flow are generally easier to test, debug, and maintain.

15 Migration checklist

  1. Classify each macro. Is it a parameterized procedure, a loop, a conditional branch, or a source-code generator?
  2. Replace macro parameters with function arguments.
  3. Replace macro variables with typed R objects.
  4. Replace %IF and %DO with if, for, while, or lapply/Map.
  5. Replace generated variable names with vectors and named lists.
  6. Replace %INCLUDE with source() or package functions.
  7. Replace macro-variable handoffs with explicit return values.
  8. Test edge cases: zero iterations, missing values, empty strings, unusual names, and type conversion.
  9. Compare outputs with SAS results on representative production data.
  10. Keep source generation only where it is truly needed.

18 18. Returning values from functions: return() and implicit return

In R, a function returns the value of its last evaluated expression unless return() is used to exit earlier. Explicit return() is useful for clarity and early exits.

double_value <- function(x) {
  result <- x * 2
  return(result)
}

answer <- double_value(10)
answer
[1] 20

The same function can omit return() because the final expression is returned automatically:

double_value <- function(x) {
  result <- x * 2
  result
}
double_value(10)
[1] 20

An early exit is a good use of return():

safe_mean <- function(x) {
  if (length(x) == 0L) {
    return(NA_real_)
  }
  mean(x, na.rm = TRUE)
}

safe_mean(numeric(0))
[1] NA
safe_mean(c(1, 2, NA, 4))
[1] 2.333333

The assignment answer <- double_value(10) stores the returned value in the environment where the assignment is evaluated. The local variable result does not become global.

19 Functions that create one data frame

A function can create a data frame locally and return it to the caller.

make_population_summary <- function(data) {
  result <- data.frame(
    n        = nrow(data),
    mean_age = mean(data$age, na.rm = TRUE)
  )
  return(result)
}

population_summary <- make_population_summary(people)
population_summary
   n mean_age
1 10     43.5

Here, result is local to the function. population_summary is created in the caller’s environment. A concise equivalent is:

make_population_summary <- function(data) {
data.frame(
  n        = nrow(data),
  mean_age = mean(data$age, na.rm = TRUE)
)
}
population_summary <- make_population_summary(people)
population_summary
   n mean_age
1 10     43.5

A function can also return a transformed data frame:

add_age_group <- function(data) {

20 Functions that create multiple data frames

When a function needs to return two or more datasets, return a named list. Lists can contain data frames of different sizes and shapes.

split_population <- function(data) {
  adults <- data[data$age >= 18, , drop = FALSE]
  minors <- data[data$age <  18, , drop = FALSE]
  
  list(
    adults = adults,
    minors = minors
  )
}

population_parts <- split_population(people)
adults <- population_parts$adults
minors <- population_parts$minors
nrow(adults)
[1] 8
nrow(minors)
[1] 2

The function returns one object—the list—which contains both data frames. The caller accesses each dataset by name.

20.1 Returning several derived datasets

build_outputs <- function(data) {
  cleaned <- data[!is.na(data$id), , drop = FALSE]
  
  summary_by_sex <- aggregate(
    age ~ sex,
    data = cleaned,
    FUN  = function(x) mean(x, na.rm = TRUE)
  )
  
  missing_ids <- data[is.na(data$id), , drop = FALSE]
  
  list(
    cleaned        = cleaned,
    summary_by_sex = summary_by_sex,
    missing_ids    = missing_ids
  )
}

outputs <- build_outputs(people)
cleaned_data       <- outputs$cleaned
sex_summary        <- outputs$summary_by_sex
records_missing_id <- outputs$missing_ids

sex_summary
  sex  age
1   F 44.8
2   M 42.2

This approach is explicit and testable. It avoids creating global variables merely to transfer results.

21 SAS DATA steps and procedures that produce datasets

SAS programs often create named output datasets as a side effect:

data work.adults work.minors;
  set work.people;
  if age >= 18 then output work.adults;
  else output work.minors;
run;

An idiomatic R function normally returns its outputs explicitly:

split_population <- function(data) {
list(
  adults = data[data$age >= 18, , drop = FALSE],
  minors = data[data$age <  18, , drop = FALSE]
)
}

result <- split_population(people)
adults <- result$adults
minors <- result$minors
nrow(adults)
[1] 8
nrow(minors)
[1] 2

SAS names output datasets in the DATA step. The R function returns a list of objects, and the caller chooses the names to which they are assigned. This makes the function reusable with different input and output names.

21.1 If the function should save datasets to disk

Creating an in-memory data frame and writing it to a file are different responsibilities. If persistence is required, make it explicit:

write_population_outputs <- function(data, output_dir) {
dir.create(output_dir, showWarnings = FALSE, recursive = TRUE)

adults <- data[data$age >= 18, , drop = FALSE]
minors <- data[data$age <  18, , drop = FALSE]

saveRDS(adults, file.path(output_dir, "adults.rds"))
saveRDS(minors, file.path(output_dir, "minors.rds"))

invisible(list(adults = adults, minors = minors))
}

tmp_dir <- tempfile("population_outputs_")
written <- write_population_outputs(people, tmp_dir)
names(written)
[1] "adults" "minors"
list.files(tmp_dir)
[1] "adults.rds" "minors.rds"

invisible() suppresses automatic printing at the console; the list can still be assigned by the caller.

22 Mapping SAS output patterns to R return patterns

SAS pattern Recommended R pattern
DATA step creates one output dataset Function returns one data frame
DATA step creates multiple output datasets Function returns a named list of data frames
PROC SQL creates a table Assign the query result to an R object, or return it
Macro variable carries a calculated result Return the value from a function
Macro creates several intermediate datasets Return a named list, or use a clear pipeline
Output dataset must be written permanently Explicitly write it with saveRDS(), write.csv(), or a database writer
Function updates an existing object Prefer returning the updated object and assigning it at the call site

Recommended principle: use a function’s return value to communicate data. Avoid assigning output datasets into .GlobalEnv from inside a function unless global mutation is an explicit design requirement.
