SAS → R Migration with DuckDB and Arrow

Practical guide: DATA STEP, PROC SQL, PROC FORMAT, joins, aggregations and Parquet

Author

Working notes

1 Introduction

This document reworks the original data.table migration tutorial around DuckDB and Apache Arrow. For each operation, the two approaches are presented in a Quarto tabset:

  • DuckDB: SQL executed from R through DBI::dbGetQuery() or DBI::dbExecute().
  • Arrow: lazy queries on Parquet datasets through arrow::open_dataset() and dplyr.

The examples use a small synthetic dataset so that every section is reproducible. The same principles apply to larger administrative and longitudinal registers, where it is important to project only the required columns, filter early, avoid unnecessary materialisation, and write intermediate results to Parquet.

1.1 0.1 Packages and shared example data

DuckDB and Arrow are different execution engines. DuckDB executes SQL and can query Parquet directly; Arrow provides columnar data structures and a lazy query interface for supported operations. dplyr is an interface, not an execution engine: the backend determines which operations are supported and where they run.

DT_base is the R object used to create the examples. DT_base in DuckDB is a registered database table; ds_base is an Arrow Dataset backed by Parquet. They contain the same rows but have different APIs and execution models.

Important distinction about memory: dbGetQuery() collects the result into an R data frame. dbExecute() executes a statement without returning a result table. Arrow collect() materialises a query in R memory; avoid it until the result is small enough or must be passed to an R-only function.

2 Selecting rows and columns

2.1 General mental model

Intent DuckDB Arrow
Filter rows WHERE filter()
Select columns SELECT select()
Group rows GROUP BY group_by()
Calculate columns SELECT expression AS name mutate()
Materialise result dbGetQuery() collect()

2.2 Filter rows and select columns

  • DuckDB
  • Arrow

  SELECT id, anno, valore
  FROM DT_base

3 Creating and modifying variables

In a database, UPDATE changes a stored table, while a SELECT expression creates a derived result. For reproducible analytical pipelines, it is often preferable to create a new table or Parquet dataset rather than mutate the source in place.

5 Labels and metadata

Neither DuckDB nor Parquet provides a direct, universally preserved equivalent of all SAS variable labels and formats. Keep metadata in a separate data dictionary.

metadata <- tibble::tibble(
  variable = c("sesso", "eta"),
  label = c("Sesso", "Età in anni"),
  source_type = c("integer", "integer"),
  format = c("sexfmt", "agefmt")

6.1 Counts and statistics by group

  • DuckDB

DBI::dbGetQuery(con, "
  SELECT cantone,
         COUNT(*) AS n,

6.2 Cross-tabulations

  • DuckDB
  • Arrow
DBI::dbGetQuery(con, "
  WITH classified AS (
    SELECT sesso,
           CASE
             WHEN eta <= 17 THEN '0-17'
             WHEN eta <= 64 THEN '18-64'
             ELSE '65+'
           END AS classe_eta
    FROM DT_base
  )
  PIVOT (
    SELECT sesso, classe_eta, COUNT(*) AS n
    FROM classified
    GROUP BY sesso, classe_eta
  )
  ON classe_eta IN ('0-17', '18-64', '65+')
  USING SUM(n)
  GROUP BY sesso
  ORDER BY sesso
")
  sesso 0-17 18-64 65+
1     1    2     2   2
2     2   NA     4   2
ds_base |>
  mutate(
    classe_eta = case_when(
      eta <= 17 ~ "0-17",
      eta <= 64 ~ "18-64",
      TRUE ~ "65+"
    )
  ) |>
  count(sesso, classe_eta, name = "n") |>
  collect() |>
  tidyr::pivot_wider(
    names_from = classe_eta,
    values_from = n,
    values_fill = 0
  )
# A tibble: 2 × 4
  sesso `0-17` `18-64` `65+`
  <int>  <int>   <int> <int>
1     1      2       2     2
2     2      0       4     2

The Arrow example uses tidyr::pivot_wider() after aggregation. Support for pivot operations can vary with the Arrow/dplyr versions; if a particular Arrow version cannot translate the operation lazily, collect the already aggregated small result before pivoting. DuckDB’s PIVOT syntax is convenient for a known set of categories.

6.3 Percentages within groups and overall

    SELECT sesso, classe_eta, COUNT(*) AS n

8.6 Complex conditional state

For state machines with several retained variables and conditional transitions, first define the ordering and state-transition rules precisely. SQL window functions are suitable for many cumulative and previous-row problems. More complex recursive logic may require a recursive CTE, a staged pipeline, or a dedicated R function. Arrow’s Dataset API is not intended as a general sequential row-by-row execution engine.

11 Missing values, PUT() and INPUT()

SAS distinguishes ordinary numeric missing . from special missings .A–.Z and ._. R’s standard missing value is NA; NaN has different semantics but does not directly represent the complete SAS special-missing system. If these distinctions carry administrative meaning, preserve them during import with an explicit status variable or textual code before normalising values.

  • SAS PUT() applies a format and returns a representation, often character.
  • SAS INPUT() reads a string using an informat and converts the value.

In R/Arrow/DuckDB, the equivalent depends on the format: CASE or a lookup table for discrete codes, CAST()/TRY_CAST() in DuckDB, and supported parsing or casting functions in Arrow. Do not assume a generic conversion reproduces every SAS informat or format.

15 Choosing between DuckDB and Arrow

Requirement DuckDB Arrow
SQL analytics and complex joins Strong fit Not its primary interface
Query Parquet without loading all rows into R Yes Yes
Lazy dplyr pipelines Through dbplyr Native Arrow dplyr interface for supported verbs
In-place database updates Yes, for DuckDB tables Not a general Parquet Dataset capability
Window functions and ordered calculations Broad SQL support Supported subset; check version
Writing Parquet COPY ... TO write_parquet() / write_dataset()
Portability of output Parquet and database files Parquet

A useful practical division is:

  1. Use DuckDB for complex SQL transformations, joins, window functions, aggregations and CTAS workflows.
  2. Use Arrow for scanning large Parquet datasets, column projection, predicate filtering and dplyr pipelines that are supported by the installed Arrow version.
  3. Use Parquet as the exchange and persistence format between stages.
  4. Collect into R only when the result is small or a downstream R function requires an in-memory object.

dbplyr can be introduced when you want to express DuckDB queries with dplyr syntax. It is not required for the SQL examples in this tutorial; direct SQL makes the execution and database semantics explicit.

16 Checklist for a SAS migration

  1. Order: check every BY, FIRST., LAST., LAG() and RETAIN; define deterministic ordering.
  2. Missing values: compare SAS . and special missing values with SQL NULL, R NA and NaN.
  3. Joins: check key cardinality, duplicate keys and row counts before and after each join.
  4. Types: check character/numeric/date conversions, precision and overflow.
  5. Formats: distinguish stored coding from display labels; version lookup tables.
  6. Aggregations: verify denominators and missing-value behaviour.
  7. Window logic: test ties, first/last rows, cumulative calculations and conditional lags.
  8. Parquet: decide whether to write one file or a partitioned dataset; avoid tiny files.
  9. Validation: compare SAS and R outputs on representative samples and edge cases.
  10. Performance: filter and project early, avoid unnecessary collect(), and inspect query plans for large jobs.
